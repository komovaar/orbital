# Orbital — цільова архітектура

Документ описує, куди має прийти кодова база: модель похідностей на полотні,
локальне виконання, готовність до мультиплеєра без переписування.

Порядок реалізації — в `orbital-plan.md`.

Основне рішення, з якого випливає все інше:

> **Граф синхронізується. Виконання — ні.**

Малий спільний стан (наміри, ребра, рішення, посилання на артефакти) живе в
журналі подій і реплікується. Великий локальний стан (репозиторії, worktree,
сесії Claude, процеси) не покидає машину людини й адресується тільки
ідентифікаторами.

---

## 1. Шари

```
┌──────────────────────────────────────────────────────┐
│  Клієнт (React + TS)                                 │
│  полотно · панель вузла · присутність                │
│  звичайний веб-застосунок, працює у вкладці          │
└───────────────┬──────────────────────────────────────┘
                │  HTTP (команди/запити) + WS (потік подій)
┌───────────────▼──────────────────────────────────────┐
│  core (TypeScript, Node)                             │
│                                                      │
│  api ──► graph ──► scheduler ──► executor            │
│           │            │             │               │
│       eventlog     context       worktree/claude     │
│           │        assembler          │              │
│        store ◄─────────────────── artifacts          │
│           │                                          │
│         sync (тільки в командному режимі)            │
└──────────────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────┐
│  Оболонка — пізніше, Electron                        │
│  вікно · запуск core · трей · оновлення              │
│  обгортка навколо того самого клієнта                │
└──────────────────────────────────────────────────────┘
```

Клієнт нічого не знає про оболонку. Він ходить у `core` по HTTP і WS, і тому
однаково працює у вкладці браузера та всередині Electron. Десктопна оболонка
з'являється пізніше й лишається тонкою — вікно, запуск, трей, оновлення.

## 2. Модулі core

| Модуль | Відповідальність | Не робить |
|---|---|---|
| `api` | HTTP-команди, WS-потік подій, присутність | не знає семантики графа |
| `graph` | вузли, ребра, свіжість, валідність DAG | жодного I/O — чиста логіка |
| `eventlog` | журнал мутацій, знімки, час, гілкування | не знає про виконання |
| `context` | збирання контексту вузла з ребер за апертурами | не викликає модель |
| `scheduler` | які вузли готові, диспетчеризація, скасування | не запускає процеси сам |
| `executor` | worktree, спавн Claude CLI, стрім подій запуску | не вирішує, що запускати |
| `artifacts` | контентно-адресоване сховище результатів | не знає структури графа |
| `store` | персистентність за інтерфейсом (SQLite / Postgres) | не містить бізнес-логіки |
| `sync` | реплікація журналу подій між воркерами й координатором | не синхронізує виконання |

`graph` і `eventlog` мусять лишатись чистими: без `fs`, `net`, `child_process`.
Це єдине місце, де живе семантика, і воно має тестуватись без файлової системи,
git і мережі.

## 3. Журнал подій — хребет

Усі мутації графа є подіями. Поточний стан — це згортка журналу зі знімками
для швидкості.

```ts
type Event = {
  id: string
  graphId: string
  nodeId: string          // подія завжди адресована сутності
  kind: EventKind
  actor: string           // хто: людина або агент
  at: string              // ISO 8601
  payload: unknown        // звужується за kind
}

type EventKind =
  | "NodeCreated" | "IntentChanged"
  | "EdgeAdded" | "EdgeRemoved"
  | "RunStarted" | "RunProgressed" | "ArtifactProduced"
  | "GateDecided" | "NodeDeleted" | "SubtreeCollapsed"
```

**Чому саме так — з цього механізму безкоштовно випливають чотири речі:**

- **Час.** Стан на момент `T` — це згортка до `T`. Часова смуга в інтерфейсі
  не потребує окремого механізму.
- **Гілкування.** Форк — це нова гілка журналу від події `T`.
- **Мультиплеєр.** Кілька клієнтів сходяться, реплікуючи журнал. Події
  адресовані вузлам, тому паралельна робота в різних вузлах не конфліктує.
- **Аудит.** Хто що зробив — властивість схеми, а не окрема підсистема.

**Це замінює `store.Update(func(state *State))` зі старого воркера.** Мутація
всього знімка під файловим локом — головна перешкода мультиплеєра: вона
перетворює просторовий поділ полотна назад на чергу.

Порядок подій усередині одного вузла — суворий. Між різними вузлами —
частковий; глобального порядку не існує й не потрібно.

## 4. Модель графа

### Вузол

```ts
type NodeKind = "source" | "derivation" | "gate" | "group" | "watcher"

type Node = {
  id: string
  graphId: string
  kind: NodeKind
  intent: string
  owner: string           // від чийого імені виконується

  artifactId: string      // посилання в artifacts, не вміст
  inputDigest: string     // відбиток входів на момент обчислення
  runId?: string          // остання сесія виконання
}
```

Стан **не зберігається** — він обчислюється з графа:

```
fresh   : artifactId !== "" && inputDigest === currentDigest(node)
stale   : artifactId !== "" && inputDigest !== currentDigest(node)
empty   : artifactId === ""
running : є активний run
blocked : будь-який предок не fresh, або незаповнений gate вище
failed  : останній run завершився помилкою
```

Обчислюваний стан прибирає цілий клас багів із розсинхроном прапорців.

### Ребро

```ts
type Aperture = "artifact" | "reference" | "normative"

type Edge = {
  id: string
  from: string
  to: string
  aperture: Aperture
  selector?: string       // яка частина артефакту джерела
}
```

**Ребро не означає послідовність.** Порядок виконання виводиться з
залежностей. Ребра типу `then` у моделі не існує.

| Апертура | Що дає приймачу | Внесок у відбиток |
|---|---|---|
| `artifact` | вміст артефакту джерела в контекст | хеш артефакту |
| `reference` | доступ до джерела без втягування | слабкий (напр. commit hash) або нічого |
| `normative` | правило, що діє на приймача і все піддерево | хеш вмісту, поширюється вниз |

### Відбиток входів

```
digest(node) = H(
    intent,
    for each incoming edge in stable order:
        (edge.id, edge.aperture, edge.selector, contribution(edge))
)
```

Свіжість — похідна від цієї функції й нічого більше.

## 5. Збирання контексту

Окремий модуль, бо саме тут лежить відмінність продукту.

Для вузла `N`:

1. Зібрати вхідні ребра.
2. `artifact` — вставити вміст джерела (або зріз за `selector`).
3. `reference` — **не вставляти**; видати виконавцю доступ (шлях репозиторію,
   дескриптор датасета) як інструмент.
4. `normative` — зібрати з усього ланцюга предків, дедуплікувати, покласти
   як правила перед наміром.
5. Порахувати бюджет і повернути розкладку по ребрах разом із контекстом.

**Ніколи не обрізати мовчки.** Перевищення бюджету повертається клієнту як
стан вузла, і людина бачить, яке ребро скільки займає. Видимий контекст — це
обіцянка продукту, а не діагностика.

## 6. Виконання

Виконавець за інтерфейсом:

```ts
interface Executor {
  run(req: RunRequest, signal: AbortSignal): AsyncIterable<RunEvent>
}
```

Реалізації:

- `command` — детермінований shell-крок; **робиться першим**, бо ним дешево
  перевіряється весь цикл графа
- `claude` — спавн CLI, розбір stream-json, відновлення сесії
- `decision` — gate: виконання немає, артефакт створює людина

Один запуск — один git worktree. Гілки-сестри отримують окремі worktree й
рахуються паралельно. Артефакт похідності — патч; він накладається
трьохсторонньо при схваленні.

**Сесія Claude належить запуску, а не вузлу.** Перезапуск вузла створює новий
запуск зі свіжою сесією і тим самим наміром. Транскрипт лишається як свідчення,
прив'язане до запуску.

**Цей шар переноситься зі старого `worker/` буквально, рядок у рядок.** Спавн,
розбір стріму, worktree, патчі, вбивання групи процесів — там немає чого
покращувати, є тільки шанс відтворити вже полагоджені баги. Спершу переносяться
тести, потім реалізація під них.

## 7. Режими розгортання

Один застосунок, два режими.

```bash
orbital serve                 # локальний: SQLite, виконує, віддає клієнт
orbital serve --coordinator   # командний: Postgres, тримає граф, не виконує
orbital serve --join <url>    # локальний воркер, під'єднаний до координатора
```

| | Локальний | Координатор |
|---|---|---|
| Граф і журнал подій | SQLite поруч | Postgres |
| Артефакти | локально | метадані + вміст |
| Репозиторії, worktree | так | **ніколи** |
| Автентифікація Claude | так | **ніколи** |
| Виконання | так | **ніколи** |

**Координатор не має ні коду, ні кредентіалів, ні виконання.** Мала поверхня
атаки, легко самостійно розгорнути, легко запропонувати хостовану версію.

Пакування локального режиму — окреме рішення пізніше: Node у комплекті
з Electron, або зібраний виконуваний файл для тих, хто ставить через `curl`.

### Від чийого імені діє агент

Найважче питання мультиплеєра тут закривається конструкцією: **вузол
виконується на локальному воркері свого власника, його кредентіалами.**
Спільні облікові дані не потрібні ніде. Координатор бачить наміри, ребра,
рішення й дифи — не ключі.

Присутність передається через WS і **не потрапляє в журнал подій** —
це ефемерні дані.

## 8. Що переноситься, що зникає

**Переноситься буквально** — це найдорожче з наявного:

- спавн Claude CLI, розбір stream-json, відновлення сесії
- git-worktree на запуск і прибирання після падіння
- трьохстороннє накладання патчів, коміти, робота з брудним деревом
- вбивання групи процесів
- **тести до всього цього — першими, як специфікація приймання**

**Переноситься з переробкою:**

- фронтендні теки `review`, `chat`, `intake`, `ui` — здебільшого як є
- `workspace` — з `tauri.invoke` на HTTP/WS-клієнт
- `canvas` — на нову модель графа

**Зникає:**

- `app/src-tauri` — вісімнадцять прохідних команд, не потрібні ні в якому
  сценарії
- `edge.kind: "then"` — послідовність виводиться, а не задається
- `store.Update(whole state)` — заміщується журналом подій
- збережені статуси вузлів — обчислюються
- модель `Mission` зі статусами життєвого циклу — заміщується вузлом
  із обчислюваним станом

**З'являється:**

- ребра як сутності з апертурами
- `context` як окремий модуль
- `gate` і `group` як види вузлів
- журнал подій і згортка
- HTTP/WS як єдиний спосіб дістатись до ядра

## 9. Порядок

Детально — в `orbital-plan.md`. Коротко:

1. Чистий домен: граф, ребра, події, обчислювана свіжість
2. Персистентність і API
3. Клієнт на HTTP, оболонка видалена — **перша демонстрована точка**
4. Мінімальний виконавець на shell-команді — **повний цикл доведено**
5. Збирач контексту — апертури стають справжніми
6. Виконавець Claude — тести першими, переклад буквальний
7. Шлюзи, групи, полотно на масштабі
8. Заміщення `main`, реліз 0.0.3

Мультиплеєр і Electron — після, окремими рішеннями. Архітектура їх уже тримає.
